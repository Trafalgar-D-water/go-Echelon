# ADR-001: Start as a modular monolith with service-ready boundaries

- Status: Accepted
- Date: 2026-09-13

## Context

Go-Echelon targets a real-time chat architecture with a REST API, WebSocket gateway, file handling, background processing, and external-content proxying. The full target topology eventually includes Delta, Bonfire, Autumn, January, Gifbox, Crond, and Pushd.

Building and operating every service from the first milestone would add avoidable complexity: several deployment units, cross-service authentication, queues, retries, observability, and local infrastructure before the basic domain rules are proven. At the same time, file handling and real-time connections have substantially different security and scaling profiles from the REST API, so permanently mixing them into Delta would create an expensive future rewrite.

## Decision

We will build the project as a **modular monolith first**, using shared core packages and explicit component boundaries. A component becomes an independently deployed service when its workload, security profile, or scaling requirements justify it.

- Delta remains the REST API process.
- Autumn is designed as the file-handling boundary and will become its own executable/container before production file uploads are enabled.
- Bonfire will be an independent WebSocket gateway once real-time delivery is implemented.
- Redis and RabbitMQ are deferred until the durable REST write path, permissions, and message model are correct.
- Shared domain contracts must live in stable core packages, not inside an individual HTTP handler or service executable.
- Service-to-service contracts must be explicit: versioned HTTP payloads or shared event schemas, authentication, timeouts, retries, and ownership rules.

## Consequences

### Positive

- The team can validate identity, permissions, server membership, and messages without premature distributed-systems complexity.
- Components with different risk profiles can later be extracted without moving domain logic out of route handlers.
- Local development remains lightweight in early milestones.

### Trade-offs

- Some later extraction work remains necessary.
- Package boundaries must be enforced deliberately; otherwise a modular monolith can become tightly coupled.
- Documentation must clearly distinguish implemented behavior from planned services.

## Revisit when

Revisit this decision when any of the following becomes true:

- File uploads/thumbnails affect Delta reliability or resource usage.
- Persistent WebSocket connections require independent scaling.
- A durable event bus is required for fan-out or push notifications.
- Separate deployment ownership is needed for a component.
