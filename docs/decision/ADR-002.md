# ADR-002: Use bitmask permissions with layered allow/deny overrides

- Status: Accepted
- Date: 2026-09-19

## Context

Go-Echelon needs server and channel authorization that is fast to evaluate, compact in API payloads, and safe to extend without changing the meaning of permissions already stored in MongoDB.

The system must support:

- Server-wide defaults for normal members.
- Multiple roles per member with deterministic rank precedence.
- Channel-specific defaults, role overrides, and member-specific overrides.
- A server-owner bypass.
- Hard restrictions such as timeouts and invisible channels.
- Future REST, WebSocket, queue-consumer, and file-service authorization checks using the same rules.

## Decision

Permissions are represented as a `uint64` bitmask in a pure `pkg/core/permissions` package.

- Each capability permanently owns one documented bit position.
- Normal permissions must use only bits 0 through 51, so permission values remain exactly representable by JavaScript `Number`.
- Existing bit positions are never renumbered or reused. A new capability receives a previously unused bit.
- `GrantAllSafe` represents all normal bits; reserved/future bits must not be assigned to ordinary roles.
- An override contains separate `allow` and `deny` bitmasks.
- Within one override, allow is applied first and deny second; deny therefore wins for overlapping bits. API validation must reject overlapping allow/deny masks.

The first implementation covers server and server-channel permissions. User relationships, direct messages, groups, voice-state synchronization, caching, and real-time fan-out will use this same foundation in later milestones.

### Resolution order

For a server channel, the evaluator applies rules in this order:

1. Server owner bypass: return `GrantAllSafe`.
2. Non-member gate: return no permissions.
3. Start with the server's `default_permissions`.
4. Apply the member's server roles from highest numeric rank to lowest numeric rank, so smaller numeric ranks are applied last and win conflicts.
5. Apply the channel default (`@everyone`) override.
6. Apply matching channel-role overrides in the same rank order.
7. Apply the channel member-specific override last.
8. Apply hard restrictions, including timeout and voice publish/receive limits.
9. If `ViewChannel` is absent, return no permissions at all.

Role hierarchy is separate from permission resolution. A capability such as `BanMembers` decides whether an actor may attempt a ban; rank decides whether the target member or role is below the actor's authority.

### Package boundary

`pkg/core/permissions` must not import Gin, MongoDB, route packages, or WebSocket code. It receives plain evaluator input values and returns a permission mask. Database and HTTP adapters are responsible for loading facts and enforcing the resulting decision.

## Consequences

### Positive

- Permission checks are constant-time bit operations after input loading.
- The same engine can be unit-tested without a database and reused by REST, WebSocket, workers, and future services.
- Channel-specific exceptions remain compact and deterministic.
- New permissions do not require data migration: existing masks simply leave the new bit unset.
- Hidden channels are protected consistently by the final `ViewChannel` gate.

### Trade-offs

- Permission bit positions become a permanent public contract and require careful documentation.
- Permission management routes must enforce both `ManagePermissions` and a delegation/rank ceiling to prevent privilege escalation.
- The evaluator needs comprehensive table-driven tests because precedence errors can create authorization vulnerabilities.
- A raw bitmask is not self-explanatory in logs or APIs; documentation and client-side constants must remain synchronized.

## Rules for adding a future permission

1. Allocate an unused bit below 52; never renumber existing bits.
2. Document the capability, scope, default value, and override behavior.
3. Add the constant and evaluator tests.
4. Add enforcement at every relevant REST, WebSocket, and background-service boundary.
5. Update API/client permission documentation.

## Revisit when

Revisit this decision if the system requires more than 52 JavaScript-safe permissions, introduces a non-JavaScript permission representation, or needs a fundamentally different authorization model such as attribute-based access control.
